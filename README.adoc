= Garland

This repository contains all my NixOS configurations.

== Configurations

All my configurations are named after poisonous plants, not because I am toxic, but because I think they are cool.

* **Foxglove**: my Framework laptop
* **Wisteria**: my desktop workstation
* **Oleander**: my homelab machine
* **Hemlock**: my VPS machine
* **Ivy**: Home Assistant running on a Raspberry PI
* **Wormwood**: AdGuard Home, the network DNS filter, running on a Raspberry PI
* **Belladonna**: Raspberry PI with Kodi for watching media

== Structure

This repository follows the https://github.com/mightyiam/dendritic[dendritic pattern]: every Nix file under `modules/` is a flake-parts module, discovered automatically with https://github.com/vic/import-tree[import-tree] (files prefixed with an underscore are skipped). Feature modules write into the `flake.modules.nixos.<name>` and `flake.modules.homeManager.<name>` namespaces, and each host (`modules/hosts/<name>`) composes the features it wants by importing them. `modules/nixos-configurations.nix` turns every `hosts/<name>` module into a `nixosConfiguration`.

== Host enrollment

Taking a machine from bare hardware to a fully enrolled host (live USB, remote install with nixos-anywhere, Syncthing, sops and the Nitrokey) is described step by step in link:docs/host-enrollment.adoc[docs/host-enrollment.adoc].

== Remote hosts

Servers are installed once with https://github.com/nix-community/nixos-anywhere[nixos-anywhere] and updated afterwards with https://github.com/serokell/deploy-rs[deploy-rs]:

[source,bash]
----
just remote-install <host> <user@address>   # first install, partitions the disk
just deploy <host>                          # every update after that, built on the host
just deploy-local <host>                    # same, but built here and copied over
----

`just deploy` builds the configuration on the host itself (only the derivations are copied, the host reuses its own store), activates it and rolls back automatically if activation fails or the host becomes unreachable. `just deploy-local` builds on the machine you are on and copies the closure; use it when custom packages need compiling on the faster machine. Both skip deploy-rs's pre-checks, which would evaluate every host configuration and not just the target.

All remote hosts are declared in one place, `modules/deploy.nix`. An entry gives the node its address and `remoteBuild = false`. That flag must stay false: the deploy-rs `--remote-build` flag can only switch remote building on, so the justfile adds it for `just deploy` and leaves it out for `just deploy-local`. The login user, the target user and the doas command are shared by all nodes and set once at the top level.

The same declaration feeds the SSH client config: every deploy node becomes a `Host <name>` alias with its address and user on all machines, so `ssh hemlock` works wherever this configuration is installed and never disagrees with the deploy target.

=== Adding a remote host

1. Add the host module under `modules/hosts/<name>` and install it, see link:docs/host-enrollment.adoc[docs/host-enrollment.adoc].
2. Add an entry to `hosts` in `modules/deploy.nix` with its address and `remoteBuild = false`.
3. Rebuild your workstation to pick up the SSH alias, then `just deploy <name>`.

=== When a deploy goes wrong

The escape hatches are deploy-rs flags, passed after the host name (`just deploy hemlock --boot`):

* `--boot` copies the closure and activates it on the next reboot.
* `--dry-activate` copies and tests the closure without switching.
* `--magic-rollback false` / `--auto-rollback false` disable the automatic rollback.

The manual fallback always works: ssh in and run `just r` in a checkout of this repository.

== Vulnerability audit

`just audit [host]` scans a system closure for known CVEs with https://github.com/tiiuae/sbomnix[vulnxscan]. Usage, the whitelist and how to treat false positives are in link:docs/vulnerability-audit.adoc[docs/vulnerability-audit.adoc].

== Secrets management

Secrets are managed with https://github.com/Mic92/sops-nix[sops-nix]. Encrypted secrets are stored in `secrets/<hostname>.yaml` and decrypted at NixOS activation time using the host's SSH ed25519 key.

=== Editing secrets

[source,bash]
----
just secrets <hostname>
----

This opens the decrypted file in your editor. On save, sops re-encrypts automatically. It only works on a machine whose age key is a recipient of that file in `.sops.yaml`; getting a new machine to that point is the last step of link:docs/host-enrollment.adoc[docs/host-enrollment.adoc].

== SSH keys and commit signing

Logins to the servers and git/jj signatures use a FIDO2 resident credential on a Nitrokey; a second Nitrokey is the backup. Public keys live in `modules/_ssh-keys.nix`. See link:docs/nitrokey.adoc[docs/nitrokey.adoc] for enrolling a machine, creating a credential on a new token and switching to the backup.
